# Autoshina Postavshiki — Агрегатор поставщиков шин и дисков

Сервис объединяет ассортимент 4 поставщиков шин и дисков в единую XML-выгрузку. Поддерживается:

- Периодическая загрузка XML по расписанию (HTTP/HTTPS)
- Адаптеры для нормализации формата каждого поставщика
- Дедупликация по характеристикам и названию
- Выбор cheapest available при дублях
- REST API: GET /export/tires.xml, GET /export/wheels.xml, GET /health, GET /ready
- Валидация `config/suppliers.yaml` и адаптеров до синхронизации; при успехе/ошибке пишется `data/sync_state.json`
- Флаг активности поставщика (active: false — не обрабатываем)
- Обработка сетевых ошибок, retry, изоляция сбоев
- Кэш: XML сначала скачивается в `data/cache/`, затем парсится (подходит для больших выгрузок)

## Установка

```bash
pip install -r requirements.txt
```

При ошибке pip в старом venv (AttributeError: ImpImporter) пересоздайте окружение:

```bash
python -m venv venv --clear
.\venv\Scripts\activate  # Windows
pip install -r requirements.txt
```

## Запуск

```bash
python main.py
```

API будет доступен на http://localhost:8000

- `GET /export/tires.xml` — выгрузка шин
- `GET /export/wheels.xml` — выгрузка дисков
- `GET /health` — liveness (процесс жив)
- `GET /ready` — readiness: валидный конфиг и последняя синхронизация без фатальной ошибки (до первого `run_sync` — 503)

Тесты: из корня репозитория после `pip install -r requirements.txt` выполните `python -m pytest tests/ -v` (полный набор модульных и интеграционных тестов без доступа к сети).

## Конфигурация

- `config/suppliers.yaml` — список поставщиков, URL, флаг active, интервал обновления, cache_dir
- `config/adapters/supplier_N.yaml` — маппинг полей и правил для каждого поставщика

### `data/sync_state.json`

Файл перезаписывается при каждом запуске синхронизации (`run_sync`): в нём последний снимок состояния для `/ready` и диагностики.

- **`categories`** — словарь по категориям загрузки. Ключи имеют вид `{supplier_id}|tires` и `{supplier_id}|wheels` и отражают **активных** поставщиков и реально обрабатываемые категории **в этом прогоне**, по конфигу **на момент этого синка**. Если после синка изменить `config/suppliers.yaml` в репозитории, содержимое уже записанного файла может **не совпадать** с новым yaml — это нормально.

- После интеграционных тестов в ключах может появиться префикс не из боевого конфига (например `keep|tires`, `keep|wheels`), если тест задаёт своего поставщика с id `keep` — это артефакт последнего запуска теста, а не ошибка синхронизации.

В файле также может быть поле **`active_supplier_ids`** — список id поставщиков с `active: true` на момент этого синка.

### Shinservice / Duplo (`supplier_3`)

Выгрузки в Duplo — это отдельные «экспорты» с уникальным токеном в URL (`…/data-export/download/<token>.xml`). Токены со временем отзываются или заменяются.

- Ответ **404** на загрузку означает, что ссылка устарела или скопирована неверно — нужно взять **новый URL** в личном кабинете Duplo/Shinservice (раздел выгрузки данных).
- Фид **шин** и фид **дисков** — это **разные** экспорты: объединённый один XML только для шин не содержит узлов `//wheels/wheel`, поэтому режим «один URL на обе категории», как у svrauto, здесь обычно **не подходит**.
- Если актуального URL для дисков ещё нет, **не задавайте** `wheels_url` в `config/suppliers.yaml`: категория будет `skipped_no_url`, синхронизация завершится без `fetch_error` по этой причине. После получения ссылки из ЛК добавьте ключ `wheels_url` снова.
- При длительном отключении загрузки дисков уже сохранённые строки этого поставщика в SQLite **не удаляются** автоматически — при необходимости очистите категорию вручную или через отключение поставщика (`active: false` удаляет его товары из БД при следующем синке).
